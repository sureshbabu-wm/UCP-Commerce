Universal Commerce Protocol

Configuration, Discovery Profiles, and Agent Card Standards Reference Guide.

1. Overview of UCP Discovery

The Universal Commerce Protocol (UCP) decouples core transactional workflows (checkout, discounts, fulfillment) from vendor-specific architectures. To interact successfully, clients and services must align on supported features, protocol formats, and endpoint locations.

UCP addresses this discovery requirement using two main artifacts:

REST / API Discovery Profile
Exposed at /.well-known/ucp
  • Announces capabilities for REST and MCP transports.
  • Hosts machine-readable OpenAPI and OpenRPC schemas.
  • Typically defined in files like discovery_profile.json.
A2A Agent Card
Exposed at /.well-known/agent-card.json
  • Functions as a public manifest for autonomous AI agents.
  • Contains organization details, preferred transports, and conversational skills.
  • Configured in files like agent_card.json.

2. Core Architectural Concepts

Spec vs. Schema

A fundamental concept in UCP discovery is the distinction between a **Specification** and a **Schema**:

Aspect Specification (Spec) Schema
Definition A human-readable documentation standard describing logic and requirements. A machine-readable structural representation (JSON Schema, OpenAPI, OpenRPC).
Primary Purpose Design reference for developers writing client and server systems. Runtime validation, auto-generating client SDKs, and routing JSON payloads.
Format HTML pages, Markdown, PDF manuals (e.g. /specification/shopping/checkout). Structured validation files (e.g. /schemas/shopping/checkout.json).

Versions and Version Anchors

Version definitions (e.g., 2026-01-23) act as anchors. The root protocol version guarantees the overarching vocabulary, whereas the component-level versions ensure individual capabilities do not drift.

⚠️

The Mismatch Problem & Contract Breaches

If a server advertises capability support for version 2026-01-23 in its discovery profile, but points to a schema file or parses requests using data structures from a different version, it causes a contract breach. A UCP client will build its JSON payloads based on the advertised schema. When these payloads reach the server, validating layers (such as Pydantic) will fail, throwing 422 Unprocessable Entity errors.

Standard vs. Custom Schemas

Standard capabilities (like UCP checkout or fulfillment) must adhere directly to official schemas. However, merchants can append custom capabilities (e.g., com.flower_shop.catalog). Because custom capabilities publish their own schema URL directly inside the profile, clients can download and validate against them on-the-fly, avoiding version mismatch failures.

Capability Inheritance

UCP capabilities are modular and use the extends field to prevent redundancy. For example, the fulfillment capability extends checkout. This layout maps directly to Python codebases: models like UnifiedCheckoutUpdateRequest configure Pydantic with extra="allow", permitting additional payload structures to wrap around core structures dynamically.

3. Configuration Document Breakdown

While REST backends rely on a single discovery profile, Agent-to-Agent (A2A) agents run with two configuration assets. Here is how they stack up:

Configuration File Context Data Layout Style Primary Role
REST Profile
discovery_profile.json		 Public REST Route Array-Based
Services map to lists of transport/version options.		 Allows one service namespace to expose multiple transport formats (REST, MCP, etc.) concurrently.
Agent Card
agent_card.json		 Public Agent Route Manifest-Based
Extensible list of skills, identity, and transport types.		 Broadcasting the agent's natural-language skills and extensions during P2P handshakes.
A2A Config
ucp.json		 Internal Server Data Nested-Keys
Legacy format: Maps namespace keys directly to configs.		 Used internally by the agent's backend (e.g. store.py) to initialize credential mappings and payment handlers.

Array-Based vs. Nested-Keys Style

The array-based style used in modern discovery profiles supports polymorphism. A single service like dev.ucp.shopping can list multiple transport mechanisms side-by-side: 

{
  "ucp": {
    "services": {
      "dev.ucp.shopping": [
        { "transport": "rest", "endpoint": "...", "schema": "..." },
        { "transport": "mcp", "endpoint": "...", "schema": "..." }
      ]
    }
  }
}

Conversely, the internal A2A ucp.json uses a direct object mapping since the agent backend acts as a single, static instance with defined specifications: 

{
  "ucp": {
    "services": {
      "dev.ucp.shopping": {
        "version": "2026-01-23",
        "spec": "https://ucp.dev/2026-01-23/specification/shopping"
      }
    }
  }
}

4. Transport Types Breakdown

The UCP discovery specification supports four distinct transport configurations:

REST
Traditional HTTP Endpoint

Requires both an HTTP endpoint and an OpenAPI schema. Clients perform state modifications via standard HTTP verbs.

MCP (Model Context Protocol)
AI-First JSON-RPC

Requires an endpoint and an OpenRPC schema. Exposes tools and data context interfaces to LLMs natively.

A2A (Agent-to-Agent)
P2P JSON-RPC Envelope

Requires pointing to an agent_card.json. Schema fields are omitted, as payload mapping happens through the agent's public card extensions.

Embedded
In-Process Library

Has no endpoint. The consumer runs the shopping engine in-memory, requiring only the API schema to route commands locally.

When you plug in a keyboard, it declares itself as a standard Human Interface Device (HID) Class. The OS understands how to receive standard letters immediately without custom drivers.

However, if your keyboard has custom capabilities—like an integrated Fulfillment OLED display or a Discounts volume dial—it must announce these extensions to the OS so correct companion software is mapped.

Similarly, in UCP, the base service (dev.ucp.shopping) is like the keyboard class. The individual capabilities (checkout, discounts, fulfillment) are the specialized features. A digital-only store doesn't support physical fulfillment, and a wholesale store might not support coupon codes. By declaring capabilities in the Discovery Profile or Agent Card, clients can build the checkout experience dynamically without requesting info that the server cannot process.

6. UCP REST Endpoints & Resource Lifecycle

UCP streamlines e-commerce APIs by consolidating modifications into a single resource lifecycle centered around the **Checkout Session**.

1. Initialize Checkout Session (Create ID)
↓
2. PUT /checkout-sessions/{id}
(Submit address, coupons, and shipping updates collectively)
↓
3. POST /checkout-sessions/{id}/complete
↓
4. GET /orders/{id}
(Retrieve finalized confirmation details)

The Single Resource Update Model

Instead of creating discrete endpoints for shipping address updates, discount applications, or courier options, the entire state is managed via PUT /checkout-sessions/{id}. The client submits the updated document, and the backend service (like checkout_service.py) calculates updates in a single atomic pass, preventing inconsistencies between items, taxes, and shipping rates.

When the order completes, the checkout session is cleared out, and a permanent order confirmation is generated. This completed order is fetched via GET /orders/{id} (defined in order.py).

7. Payment Handlers and Signing Keys

Actual processing of payments is delegated to dedicated modules called **Payment Handlers** (e.g., Google Pay or Shop Pay).

Integrating these handlers securely depends on two primary concepts:

1. Webhook Callbacks

When a customer authorizes a transaction inside a payment instrument, the payment handler processes the funds and notifies the UCP merchant server asynchronously using webhook endpoints.

2. Cryptographic Signing Keys

To prevent unauthorized parties from spoofing checkout completions, webhook payloads must be authenticated. The payment handler signs the webhook body using a **private key**. The merchant server validates the signature using the corresponding **public key** (registered in the signing key configuration), establishing a secure trust boundary.

9. Debugging and Troubleshooting Discovery

If you suspect the discovery mapping or version handshake is failing:

Using Debug breakpoints

You can insert a Python breakpoint inside the discovery service route handler discovery.py: 

# Insert breakpoint in discovery.py
def get_discovery_profile():
    breakpoint()
    return load_profile_from_disk()

Pdb Commands Reference

Once the interpreter interrupts execution, run these commands in your debugger command line to inspect values:

  • p profile - Print the parsed profile dictionary.
  • p profile["ucp"]["capabilities"] - Check configured capabilities.
  • n - Step to the next line.
  • c - Continue execution.
